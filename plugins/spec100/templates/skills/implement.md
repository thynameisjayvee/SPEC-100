---
name: spec100-implement
description: Implement a selected plan using project agents, independent review, and evidence gates.
disable-model-invocation: true
argument-hint: "<topic>"
---

Read context, learnings, all rules, the selected plan, and `harness/.runtime/protocol.md`. Resolve ambiguous plans before acting. All runtime commands below run in the project root. Use the current Claude session ID for `--session` when available; never invent one.

1. Start a run with `workflow start --topic <topic> [--plan <relative-plan>] [--session <session-id>]`, or resume its existing record. Never reset a run or its three-round cap. Inspect unrelated user changes and preserve them.
2. Obtain destination, reason, cost, next-action, and environment checkpoints from each agent before it works. Record each agent's checkpoints immediately. Delegate implementation to `spec100-implementer`. Keep orchestration and evidence writes in this parent conversation. Reviewers/verifiers remain read-only; independent reads may run in parallel, and writes must have disjoint ownership or run serially.
3. For software work, run baseline verification before changing project files and record `preflight` evidence. Run project tests/builds appropriate to the plan; a command failure or unavailable required check blocks progress. Do not record absent tests as successful executions.
4. Ask `spec100-risk-classifier` to assess the proposed steps before implementation and the actual changes before delivery. Record risk. Authentication/security changes, migrations, destructive operations, production configuration, and uncertain risk are high. Obtain the user's explicit approval **before** a high-risk action, explaining the concrete action and rule requiring approval. Only after approval, invoke `workflow approve` with the user's response and reason. The runtime tool hook also requests native permission. Approval is tied to the current plan and change fingerprint. Do not approve on the user's behalf. Re-check approval before each high-risk action; changes invalidate it.
5. Execute plan units through the implementer. After implementation, run pre-PR verification and record `verification` evidence against the current changes.
6. For each software review round, delegate independent code review to `spec100-code-reviewer` and security review to `spec100-security-reviewer` in parallel. Give both the same plan and current diff; include untracked changes and relevant pre-existing changes. Review results must identify specific defects, locations, severity, and reproduction/evidence.
7. For every finding, delegate to two independent invocations of `spec100-verifier` using distinct IDs. They must not be either reviewer. Each votes confirm/dismiss with evidence. Both must dismiss a finding to clear it; disagreement remains unresolved. Record the complete round before remediation, even when findings exist. Do not omit disputed findings. A round with no findings still records both reviewers.
8. Remediate confirmed/disputed findings and re-verify/re-review. The first review is round one; maximum three total rounds. After round three, unresolved findings produce a blocked handoff with risks and next actions. Do not run a fourth review or create another topic to evade the cap. When code changes after a previously clean third review, hand off blocked because its evidence is stale.
9. For software work, perform applicable UAT and attach screenshots in the topic directory. Record its scenario and outcome. Explicitly record why UAT is inapplicable when it is; lack of tooling or failing tests is a blocker. Record detection signals and concrete rollback steps without executing destructive rollback.
10. Refresh risk and approval for final changes as needed. Record all agent checkpoints, append operational lessons through `learn`, and run `workflow check --topic <topic>`. Once it passes, run `workflow finish --topic <topic>`, then `/spec100:check`. Report changed behavior, verification, evidence locations, and any limitations. If blocked, report the blocked state candidly. Never fabricate tests, agent identities, votes, screenshots, or approval.

Do not create PRs, merge, deploy, reset a dirty checkout, or create a worktree automatically. Non-software projects still require implementation checkpoints, risk assessment, and high-risk approval, but software-specific review/UAT gates do not apply.
